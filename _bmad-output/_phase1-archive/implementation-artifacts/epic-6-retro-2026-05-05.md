## What Went Well

### 1. Hard Architectural Gate Paid Off

The Story 1.2 PixiJS spike (60fps validation gate) was the right call. We confirmed WebGL performance on mid-range hardware *before* any tree work began. No stories were built on a foundation that couldn't perform. The gate cost one story's worth of work upfront and saved potential rework across all of Epics 1, 3, and 5.

### 2. Research Spikes Prevented Wasted Implementation

Story 1.3a (game data source research) discovered that tunklab.com / community JSON was the viable path before we built any parser. More importantly, Story 1.3a's research also surfaced the build code import problem (no pasteable format exists) early enough to defer Story 2.1 cleanly rather than discovering it mid-implementation.

### 3. Streaming Architecture Was Elegant

The Claude API → SSE → Tauri events → `useOptimizationStream` → Zustand pipeline worked better than expected. Suggestions render incrementally, errors surface cleanly, and the frontend never blocks. The NDJSON-over-SSE approach with strict line buffering in Rust was the right call.

### 4. Props-Only SkillTreeCanvas Isolation Held Up Across All Epics

The decision to keep `SkillTreeCanvas` receiving everything via props (never accessing stores) prevented a category of bugs. PixiJS ticker callbacks run outside the React render cycle — having any store access inside the PixiJS context would have caused stale-closure or concurrency issues throughout Epics 1, 3, and 6.

### 5. Test Suite Grew Meaningfully

Started at 60 tests after the initial QA pass. Ended at 465. Each story added real coverage (not snapshot tests), and axe-core CI integration in 6.2 means accessibility regressions now fail the build automatically.

### 6. Deferred-Work Discipline

Every code review surfaced deferred items into `deferred-work.md` with context. This prevented "we'll fix it later" decisions from evaporating. The deferred list is now a prioritized backlog for post-MVP polish rather than a pile of forgotten TODOs.

## Challenges & Growth Areas

### 1. Domain Knowledge Gap: No Build Code Import Format

The biggest planning miss of the project. Story 2.1 (build code import) was in Epic 2 as a primary path, but no pasteable build code format exists for Last Epoch. `lastepochtools.com` uses server-side URL hashes; save files use numeric node IDs with no public mapping. This wasn't discovered until the 1.3a research spike.

**Lesson:** For tools targeting specific games, a domain feasibility check for *each planned integration point* should happen before PRD finalization, not during the first research spike of Epic 1.

### 2. Headless UI v2 `data-[focus]` vs `focus:` Confusion

Multiple components (GoalSelector, SkillTreeTabBar, SavedBuildsList) had invisible focus rings because Headless UI v2 uses `data-focus` attribute rather than `:focus` CSS pseudo-class. `focus:outline-none` suppressed the global ring and no `data-[focus]:` replacement was added. This was only caught in 6.2's axe audit.

**Lesson:** Document Headless UI v2's focus model in project-context.md at project start. Any new Headless UI primitive must use `data-[focus]:` prefix for focus indicators, never `focus:`.

### 3. Stronghold Sequential Read Constraint Discovered Late

The `tauri-plugin-stronghold` vault cannot handle concurrent opens. This constraint wasn't documented upfront — it was discovered during Story 5.1 implementation when `Promise.all()` on two vault reads produced a lock error. The `App.tsx` startup now chains reads with `.then()` sequentially.

**Lesson:** Plugin concurrency constraints should be documented in architecture.md during the Solutioning phase, not discovered during implementation. This is now captured in project-context.md.

### 4. PixiJS v8 API Breaking Changes Underdocumented

The WebGL `getShaderInfoLog` null return patch, the `Graphics` method chaining changes, and `@pixi/react` being installed but not usable as JSX components — all of these were discovered during Story 1.2 and 1.4, not anticipated in architecture. The architecture doc had "PixiJS v8" but not its specific breaking changes from v7.

**Lesson:** For any library major version upgrade (v7 → v8), a brief migration notes section in the architecture doc prevents the team re-discovering the same API differences.

### 5. Epic 6 Scope Was Right but Felt Like an Afterthought

Accessibility was an explicit requirement from the start (NFR15–17, UX-DR15), but the actual implementation (axe CI, ARIA infrastructure, keyboard nav) landed in the final epic. The result is correct, but several a11y patterns (focus rings, live regions, Headless UI `data-[focus]`) would have been easier to implement consistently if seeded in Epic 1's scaffold and enforced earlier.

**Lesson:** Add axe-core CI from Story 1.1 (even with zero a11y tests, just the infrastructure). Seed `aria-live` region divs in the App scaffold. This shifts accessibility from "Epic 6 feature" to "continuous constraint."

### 6. Code Review Always Found Real Issues

Every single code review applied patches — never a clean pass. The pre-existing double-emit pattern in `invoke_claude_api`, the contextmenu listener leak in 6.2, the Argon2 blocking the async executor — these were all caught in review, not by the original implementer.

**Lesson:** The adversarial code review step in the BMAD workflow is genuinely valuable and must not be skipped under schedule pressure.
